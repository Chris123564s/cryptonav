## Git 仓库损坏事件与恢复（重要，环境反复出现）
- 现象：`git status` 报 `fatal: bad object HEAD`；`cat .git/refs/heads/main` 指向一个缺失的提交对象（被环境的外部进程删了对象/refs）。一次 `git pull --rebase` 被 SIGTERM 打断，.git/rebase-merge 残留。
- 诊断：`git fsck --no-reflogs | grep dangling` 看本地悬空提交；`git ls-remote origin main` 取得真实远程 tip。
- 关键判断：远程 tip（本次 5fd3ddf）的完整历史（rev-list --count = 130）本地都在，只是 main 引用指针坏了。
- 恢复步骤（有效）：
  1. `rm -rf .git/rebase-merge .git/rebase-apply`
  2. `git update-ref refs/heads/main <真实远程tip>`  ← 把坏指针指回有效提交
  3. `git reset --hard <真实远程tip>`  ← 同步 index+worktree
  4. `git checkout -f HEAD -- .`  ← 强制把缺失的跟踪文件从 HEAD 还原回磁盘
  5. 重新写入被 reset 清掉的未跟踪文件（本次 bitmedia 文件），再 add/commit/push。
- 教训：本仓库对象库会被环境动，push 前若落后先 `git fetch`；rebase 中途被打断易留损坏态，优先用 update-ref 重建指针而非反复 pull --rebase。
- 注意：仓库根有遗留未跟踪文件 `home_tmp.html`（~219KB），不要误提交；它不在 public/ 故不会被部署。

### ⚠️ 验证线上邮箱的坑：Cloudflare Email Obfuscation（重要，别再踩）
- **不能**用 `curl 页面 | grep 邮箱` 验证线上！Cloudflare 的 Email Obfuscation 会把页面里所有邮箱加密成两种形态：
  - `<a href="/cdn-cgi/l/email-protection#<hex>">`
  - `<span class="__cf_email__" data-cfemail="<hex>">[email&#160;protected]</span>`
- 结果：HTML 里**没有任何明文邮箱**，`grep contact@` 和 `grep hello@` **都返回 0**。本次就误以为"部署没生效/新旧都没有"，差点去反复排查一个根本不存在的问题。**新旧都是 0 不等于没部署，只等于被混淆了。**
- 解码算法：hex 串**首字节是 XOR key**，从第三个字符起每两个字符（1 字节）与 key 异或，得到明文字符。
- 已固化为常驻工具 `scripts/check-cf-email.py`（urllib 自抓 + 解码 + 断言）：
  - `python scripts/check-cf-email.py` 默认查 6 个关键页；也可传任意 URL；`--expect <addr>` 指定期望地址。
  - 全部匹配输出 `RESULT: PASS` 且 exit 0，出现其他地址则标记 `[BAD]` 并 exit 1（可挂 CI 做发布后检查）。
  - newsletter 的 mailto 带 `?subject=...` 后缀，脚本比较前会截断 query，不会误报。
- 附带坑：本沙箱 `curl` 直接管道给 grep 会拿到 `HTTP 200` 但 `SIZE=0`（输出被吞，见更早的 /tmp 写文件故障）；必须 `-o` 落盘再 grep。python urllib 无此问题，故工具用 urllib 而非 curl。
