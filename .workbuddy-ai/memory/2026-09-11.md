## 🔴🔴 沙箱把 `.git` 毁了一次（第二次删目录事故，比 `src/` 那次更严重）

**症状**：`git merge` 突然 `SIGTERM` 且零输出 → 之后 `git log` 报 `not a git repository`。
`.git/` 目录还在，但 **`refs/` 整个目录 + `objects/pack/*.pack` 全被删**，只剩 `.idx`
（僵尸索引）和 5 个松散对象。`objects/pack` 与 `refs` 的 mtime 都指向事故时刻。

**为什么会毁**：极可能是沙箱的 safe-delete 守卫拦截了 git 内部删除 ——
`git fetch` 写新 pack 时会删旧 pack，`git merge`/`gc` 也会删对象。**git 的自我维护
是批量删除，正好撞在守卫上。**

### 恢复步骤（已跑通，务必按序）
1. **先备份**：`cp -r .git .git-backup-$(date +%s)`（此时 .git 很小，只有几十 KB）。
2. **别慌，reflog 是命根子**：`.git/logs/refs/heads/main` 没被删，
   完整记录了每次 ref 变更 → 能查出 HEAD 到底是哪个 SHA。
3. **重建 refs**：`mkdir -p .git/refs/heads && echo <sha> > .git/refs/heads/main`。
4. **清僵尸索引**：`objects/pack/*.idx` 若无同名 `.pack` 就移走，
   连同 `multi-pack-index`。**不清的话 `git fsck` 会刷屏 28 条 `failed to load pack entry`**，
   掩盖真正的问题。
5. **重新拉取**：`git fetch origin "+refs/heads/main:refs/heads/_restore"`
   （⚠️ **不能 fetch 进当前 checkout 的分支**，git 会拒绝：`refusing to fetch into branch`）。
   这一步会拿回全部历史对象（72MB pack）。
6. **用 `git reset --mixed <远端sha>` 重建基线**，工作树不受影响（**绝不用 `--hard`**）。
7. 重新 commit 工作树里未推的内容 → push。

### ⚠️ 三个新踩的坑
- **`refs/remotes/` 的写入在这个沙箱里不持久**：fetch 明明报 `[new branch] main -> origin/main`，
  几秒后 `origin/main` 又没了 → `merge: origin/main - not something we can merge`。
  **对策：用本地分支做中转**（`_restore`），别依赖 remote-tracking ref。
- **推送失败的真正原因可能不是网络**。`fatal: bad tree object <sha>` 才是关键 ——
  某个 commit 的 tree 缺了。用 `git fsck --full | grep "broken link"` 能直接指出
  **是哪个 tree 链到了缺失对象**。我这次是 `01f00443`(= `0ea689f` 的 tree) → `3f256081` 缺失。
- **缺失对象若属于未推的提交，最简单的解法是丢掉那个提交**（内容已在工作树里，
  用 `git reset --mixed` 到远端基线后重新 commit 即可），比 `commit-tree` 重新挂父节点省事。
- **push 会偶发挂死**（`timeout 240` 后 exit=124，零输出），重跑一次就 2 秒过了。
  **别因为一次挂死就判定推不上去。** 用 `GIT_TRACE=1` 能看到它卡在 `pack-objects`。

### 损失评估：**零**
工作树完好（src 60 / functions 5 / scripts 39 / public 432 / supabase 1 / .github 7 个文件），
远端有完整历史。**线上站点全程未受影响。** 教训同 `src/` 那次：**做批量 git 操作前先提交并推送。**

## 🔴🔴 发现并修复：`/api/submit` 是「一发请求永久停更」的开关

**这是本轮最有价值的发现，优先级高于 6 个联盟码。**

### 机制
`src/pages/verify/[slug].astro` 的 `getStaticPaths` 遍历的是**全部** `projects`，
而页面顶部有个**致命守卫**：

```js
const s = getSafety(project.id);
if (!s) throw new Error(`no safety record for ${project.id} — run scripts/build-safety-report.mjs`);
```

`POST /api/submit` 是**公开、无鉴权**的，它往 `projects.json` 追加一条
`status:'pending'` 的项目 —— 而安全报告是**定时**重建的，新 id 当然还没有记录。于是：

1. 访客提交一次 → `projects.json` 多一条 pending
2. `astro build` → `getStaticPaths` 把它也算进去 → `getSafety()` 返回 null → **`throw`**
3. **坏条目留在 `projects.json` 里 → 之后每一次构建都失败**
4. CF 会继续用上一个好版本（站点不挂），但**整个站点彻底停止更新**，且**不报错**
5. 攻击者可以反复提交、不断重置窗口 → **永久停更**

**这就是 9-06 那次部署失败的真因**（提交 `86f8ee6`，我探针写进去的 `t` 条目）。

### 修复（已实测）
- `verify/[slug].astro` 和 `embed/[slug].astro` 的 `getStaticPaths` 改用
  `getActiveProjects()`。**提交永远被写成 `pending`，所以永远进不了这个循环。**
- **那个 `throw` 故意保留** —— active 项目缺记录是真错误，值得让构建失败。
- `check-safety.mjs` 里三处「每个项目都要有记录」的假设改成「每个 **active** 项目」
  （否则一次正常提交就会污染 `npm test` 链）。
- **加了源码级守卫**：断言这两个页面的 `getStaticPaths` 块里含 `getActiveProjects()`
  且不含 `projects.map`。注释拦不住人，测试可以。

### 验证方式（可复现）
注入一条与 `/api/submit` 写入格式**逐字一致**的 pending 条目（`__dos_probe__`），然后：
| 检查 | 结果 |
|---|---|
| 旧逻辑 `projects.map()` 缺记录 | `__dos_probe__` → **throw ❌** |
| 新逻辑 `getActiveProjects()` 缺记录 | 无 → **通过 ✅** |
| 带恶意条目跑完整 `npm run build` | **成功**，`no safety record` 报错 **0 次** |
| 带恶意条目跑 `test:safety` | 1334 断言全过 |

数据已还原（63 条），工作树只剩预期改动。
⚠️ `npm run build` 仍报 `BUILD_EXIT=1` —— 沙箱守卫的已知假失败，日志里三处 `✓ Completed`。

### 顺带修正的另一件事：`embed` 页也有同样遍历
它用可选链（`s?.grade ?? ''`）所以**不崩**，但会给未审项目生成一个

### ⭐ 孤儿页的精确机制（比我第一版说得更准）

`chains.json` 顺序：`1=ethereum … 8=optimism 9=sui 10=ton`。**同一个 `slice(0, 8)` 出现在两处**：

- `Header.astro:5` → `chains.slice(0, 8)`：sui/ton 无导航入链。
- `chain/[slug].astro:21` → `chains.filter(c => c.id !== chain.id).slice(0, 8)`：
  - 前 8 条链的页面，filter 掉自己后第 8 个位置正好由 **sui** 补上 → **sui 拿到 8 条入链**；
  - 但 **sui 自己**的页面，filter 掉 sui 后前 8 个又变回那 8 条导航链 → **ton 从此不在任何页面列表里**。

### 🔴 推送挂死的真因找到了：PortableGit 的 `credential-helper-selector`（推翻旧归因）

这次 `git push` 连续两次 SIGTERM、零输出。`GIT_TRACE=1` 后真相很清楚：

```
12:29:13  run-command: echo .../etc/gitconfig
12:30:40  run-command: git-credential-manager.exe get     <-- 中间空了 87 秒
```

`tasklist` 抓到 `git-credential-helper-sel.exe` 卡在那里，`git-remote-https.exe` 干等。
根因是 **PortableGit 的**系统级 gitconfig 写死了 `credential.helper = helper-selector`：

```
file:.../PortableGit/.../etc/gitconfig    helper-selector          <-- 卡住的是这个垫片
file:C:/Users/a/.gitconfig                git-credential-manager   <-- 这个是好的
```

**旧结论"卡在 pack-objects"是错的** —— 那次可能是另一回事，这次有 trace 实证。

**修法（重置 helper 列表，只留 GCM，之后几秒就过）**：

```bash
git -c credential.helper= -c credential.helper=manager \
    -c http.proxy=http://127.0.0.1:$PORT -c https.proxy=http://127.0.0.1:$PORT push origin main
```

**诊断一行**（应立刻返回；卡住就是垫片的问题）：
`printf 'protocol=https\nhost=github.com\n\n' | git -c credential.helper= -c credential.helper=manager credential fill`

结果：`41e79ed..58b4dc9  main -> main` ✅（`58b4dc9` = 审计脚本 + 报告 + 记忆）。
**以后推之前直接带上 `-c credential.helper= -c credential.helper=manager`，别再等 4 分钟。**
