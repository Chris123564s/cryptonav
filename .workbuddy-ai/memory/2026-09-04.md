## 🚨 本地 git 仓库被 rebase 中断搞坏（14:02，重要教训）

**起因**：`git fetch origin main` 后跑 `git rebase FETCH_HEAD`，命令被 **SIGTERM** 打断。

**后果**：`.git/refs` 目录整个消失 → `git rev-parse` 直接报 `not a git repository`；
随后 `git fsck` 报**大量 missing blob**，连 tree 也读不到（`unable to read tree`）。

**根因推断**：
1. rebase 要移动分支指针，沙箱对 `.git/refs/*` 的写入被拦/被打断；
2. fetch 下来的 pack 是 **thin pack**，`index-pack --fix-thin` 补全步骤被 SIGTERM 打断，
   导致 pack 不完整 → 大量对象缺失；
3. 更糟的是 safe-delete 钩子可能在清理时动了 `.git/objects` 的松散对象
   （`ls .git/objects` 只剩 6 个前缀目录，正常应有几十上百个）。

**修复路径**（已验证可行）：
1. `mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin` → 让 git 重新认仓库；
2. `git fsck` 找到 dangling commit，但本地未推送的 commit（6792780）**已丢失**；
3. 放弃修本地对象库（tree 也缺），改为**重建 git 元数据**：
   - `mv .git .git-broken-<ts>`（隔离，可回滚）
   - `git clone --no-checkout <remote> <临时目录>`
   - 把临时目录的 `.git` 移回来
   - `git reset --mixed HEAD` 重建 index（工作区文件不动，全部保留）
4. 工作区文件**始终完好**，唯一损失是那个未推送的 commit（改动只有 1 行，重做即可）。

**⚠️ 纪律（下次必须遵守）**：
- **永远不要在这个环境里跑 `git rebase`** —— 它是唯一会批量重写 `.git/refs` 与对象的操作，
  一旦被 SIGTERM 就会毁掉本地对象库。
- 替代方案（已验证）：本地没有需要保留的未推送提交时，用
  `git fetch origin main` + `git reset --mixed <remote-tip>` + 重新 commit，
  效果等价且只写 index，不动 objects。
- 若确实有未推送提交要保，先 `git format-patch` 导出到工作区再操作。
- clone 大仓库会超过 120s 前台超时 → **必须 `run_in_background`**；
  超时残留目录 bash `rm -rf` 删不掉，换 PowerShell `Remove-Item -LiteralPath -Recurse -Force`。
