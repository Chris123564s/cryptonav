### 实测发现（全部可复现，不是主观感受）

**内容结构**
- 46 页 / 38,038 词 / **中位 584 词** —— 低于 2026-06 核心更新后的「150 页主题深度」红线
  （该更新后 <150 页单主题站出现类目级崩塌，200-2000 页中型站掉 40-70%，权威站 +15-35%）

- **一手经验信号 0/46 页** —— YMYL 领域最致命。有一手经验信号 +38% 可见度，
  纯 listicle -63%

**技术**
- `cf-cache-status: DYNAMIC`，HTML **从不走 CDN 缓存**（连测 3 次）
  - 根因（Cloudflare 官方原文）：「一旦 Pages 项目加了 Functions，**默认所有请求都会调用

**SEO 基础面**

  无 hub-and-spoke，权重无法集中；`/chain/ton` 内链数为 0

### 数据源实测结论（反复踩坑得出，别再试错）
1. **RDAP**：IANA 引导文件**不含 .io / .co**。.io 走 `rdap.identitydigital.services/rdap/`
   可通；.co 全端点不可达（theblock.co 因此永久无域名年龄）。Verisign 会限流，需重试。
2. **GoPlus 免费档一次请求只返回 1 个地址**，传 15 个也只回第一个 → 批量请求会**静默丢弃**。
   必须逐地址请求。
3. **DefiLlama /hacks 的 `defillamaId` 在 CEX/钱包类事件上大量缺失**（Binance $570M、
   Kraken $10.4M、Bitget $100M 全无 ID），且协议按版本拆 ID（Aave V1–V4 是 4 个）。
   只能人工策展归属，但**金额/日期全部实时取自源数据**。
4. **Wayback CDX 在沙箱代理下不可达**（web.archive.org 被白名单拦截），CI 里应可用。
5. 沙箱代理只放行部分 host：binance.com / aave.com / uniswap.org 均 `fetch failed`，
   这是**环境限制不是站点问题**，探针要用 SKIP 而非 FAIL 区分。

### 三个致命陷阱（都是"数据看起来对但实际会毁掉产品"）
1. **域名注册时间 ≠ 项目年龄**。solana.com=1993、base.org=1996、bybit.com=1999、
   ledger.com=1994、dune.com=1997、aave.com=1997、sushi.com=1999 — 全是二级市场买的
   溢价老域名。直接拿来算年龄 = 公开写「Solana 运营 33 年」。
   → 对策：以 Wayback 首次抓取为准；无 Wayback 且注册日早于 2008-10-31（比特币白皮书）
   时，`operatingSince` 置 null（不发布运营年龄）+ 分数打 0.4 折 + 页面显示警告。
   **域名注册日期仍作为事实展示，但标注它不是项目年龄。**
2. **DefiLlama 文本匹配会诬告**。"Blur Finance"（BSC 跑路盘）≠ Blur.io、
   "Phantom Galaxies"（NFT 游戏）≠ Phantom 钱包、"Safe Dollar" ≠ Safe{Gnosis}、
   "Solido Cash" ≠ Lido、"RocketSwap/Grand Base" ≠ Coinbase 的 Base、
   "AVE" 撞 Aave/Agave/xAVE/Save。→ 人工策展 + REJECTED_MATCHES 作为数据发布。
3. **低覆盖度反而拿满分**。MEXC 只有 1 个维度有数据，却因「无事件」得 100 分。
   → 二维度门槛（<2 个维度不评分）+ **分数封顶于覆盖度**（只验了 75% 的评分项，
   最多只能得 75 分）。封顶前 17 个项目并列 100 分，封顶后分布 58–98。
   「我们明明写着这不是审计，却给满分」是最不能犯的错。

### 评分模型
- longevity 35% / incidents 40% / contract 25%
- 缺失维度**权重按比例重分配**（无代币的 CEX 不因没有代币被扣分）
- 维度分先归一化到 0–100 再加权（曾漏掉这步，导致满分只有 32.7）
- 事故惩罚 = 严重度(按金额分档) × 时间衰减(1年内1.0 / 1-3年0.8 / 3-5年0.6 / >5年0.4)
- 结果：A 11 个（全是 100% 覆盖的代币项目）/ B 44 / C 7 / 未评级 1（The Block）

## 评分模型修正：覆盖率硬上限 → 先验收缩（commit 5213991）

### 触发
做分布图时发现 **62 个已评级项目里有 33 个都是 75 分**。

### 根因
`total = Math.min(raw, coverage)`。63 个项目里 45 个是 75% 覆盖率（域名+事故，无代币），
上限把其中 33 个全部钉死在 75。

**教训：又是一次「看输出才发现」的 bug。** 之前三次（维度未归一化、单维度满分、
把我们的基础设施故障算进扣分）也都是跑了才暴露。评分模型必须看分布，不能只推逻辑。

### 改法
```
total = raw × coverage + PRIOR × (1 - coverage)
```
保留原意图（部分数据拿不到满分），恢复区分度。PRIOR 取值**跑数据标定**出来的：
- 55 → A 26 / B 21 / C 15（A 太多，三项自动检查撑不起 42% 的 A）
- **50 → A 19 / B 36 / C 7** ← 采用
- 45 → 同 50；40 → 开始出现 D

### 顺带修的第二个问题
域名注册早于比特币的旧规则是 `discount = 0.4`，等于**把我们的数据缺口算成项目风险**。
结果：Solana / DeBank / Dune / CoinDesk（零事故）和 Binance（$6.1 亿）同分 67。
→ 改 `discount = 0.5`（中性：无证据时假定平均）。仍有区分：可验证年龄的项目仍排在前面。
这与之前修的「Binance 因 Wayback 挂掉被扣分」是同一类错误，之前只修了一半。

### 结果
33 个同分 → **20 个不同分值，区间 60–98**，A 19 / B 36 / C 7 / 未评级 1。
垫底：Bybit 60（$14 亿）、Bitget 60、Kraken 64、OKX 66、Ledger 66 — 全是有真实事故的，排序正确。

### 新增护栏（check-safety.mjs，1298 → 1345 断言）
- 覆盖率 <100% 时分数必须 <100（部分数据不能满分）
- 任一单个分值不得超过目录的 1/3（防同分墙再现）
- 不同分值的数量 ≥ 项目数的 1/3

### 注意
`operatingSince` / `ageYears` 在数据里但**页面从未渲染**——这是对的。
页面只说 "domain registered on X" 或 "first captured online X"，从不声称项目运营了多久。
Blur 域名 2013 年注册但项目 2022 年才上线，这个 9 年误差只能靠 Wayback 在 CI 里纠正，
不能手工打补丁（那又回到手写断言的老路）。

## 部署故障根因定位与修复（本轮，已推送 9885cd4）

### 报错
```
Failed: an internal error occurred. If this continues, contact support
Error: Failed to publish assets.
```
**关键点：构建成功、只有发布资源阶段失败。** 所以本地 `npm run build` 永远全绿，
排查方向必须落在「产物本身」而不是「构建过程」。

### 根因：public/logos/dex 无上限累积
`scripts/fetch_dex_wins.py` 每天下载 DexScreener 涨幅榜代币的 header 图：
- 只判断了下限 `len(img) > 200`，**没有上限**
- 一律存成 `.png`，但 DexScreener 的 header 很多是**动画 GIF**（魔数 GIF89a）
  —— 单个「代币图标」最大 7.46 MB
- **从不删除旧文件**，每天加几个，攒到 106 个 / 45 MB，而 wins.json 只引用 7 个
  → 99 个孤儿

dist 因此涨到 **67 MB / 695 文件**。清理后 **21 MB / 596 文件**。

### 排查方法（可复用）
1. `du -sh dist` + `find dist -type f | wc -l` 看总量
2. `find dist -type f -printf '%s\t%p\n' | sort -rn | head` 找大文件
3. **用 PNG 头解析宽高验证文件是否真的是 PNG**：解析出 `33x4278931013` 这种
   荒谬值 → 说明根本不是 PNG。`head -c 6 file` 看魔数即可（GIF89a / \xff\xd8\xff / \x89PNG）
4. 对比「目录里的文件数」vs「数据文件里引用的数量」→ 差值就是孤儿

### 教训
- **只设下限不设上限的检查等于没检查。** `len(img) > 200` 挡住了错误响应，
  放过了所有超大文件。
- **自动生成的文件必须有对应的清理机制**，否则 dist 会静默膨胀到部署失败。
- **本地 build 绿不代表能部署。** 需要 `check-dist-size` 这类门禁盯产物体积
  （阈值：总 40 MB / 单文件 20 MB / 5000 文件），比 Cloudflare 硬限制
  （单文件 25 MB / 20000 文件）更紧，好在有征兆时就发现。

## Cloudflare Pages 部署失败：`Failed to publish assets`（第二轮，推翻第一轮结论）

### 第一轮结论是错的
我之前判定「产物体积过大」是根因，把 `dist` 从 67 MB 清到 21 MB。**实测证伪**：

用 `git worktree` 检出最后一次成功部署的 `2e624fa` 单独构建：

| 版本 | 文件数 | 体积 | 结果 |
|------|--------|------|------|
| `2e624fa`（最后成功上线） | 568 | **61.53 MB** | ✅ 成功 |
| 当前 HEAD | 630 | **21.89 MB** | ❌ 失败 |

**61 MB 成功、21 MB 失败** → 体积不是原因。
（清理 dex logo 仍是对的——那是真 bug，只是不是这次的解药。）

### 逐项排除（这套方法可复用）
| 假设 | 结论 | 判据 |
|------|------|------|
| 总体积 / 单文件 / 文件数 | 排除 | 上表；最大文件 5.06MB < 25MB；630 < 20000 |
| `_routes.json` 格式 | 排除 | 官方文档三约束全满足（≥1 include、≤100 规则、≤100 字符） |
| `_headers` 格式 | 排除 | 已在线上生效，见下 |
| 非法 UTF-8 / NUL / 空文件 / 非 ASCII 路径 / 大小写冲突 | 排除 | `scripts/scan-dist-integrity.mjs` |
| `build` 脚本被改 | 排除 | 一直是 `astro build` |
| Actions 抢跑 | 排除 | 5 个 workflow 全 schedule+dispatch，无 push |

### 三个关键诊断手法（值得复用）

**1. 用「静态 vs Functions 响应头」判断 `_headers` 是否生效**
官方文档：_headers 只作用于静态资源，不作用于 Pages Functions 响应。于是：
- 静态资源 `/admin/config.yml` → 有 `x-content-type-options: nosniff` + `referrer-policy`
- Functions `/api/cg/global` → 两个头都没有

「静态有、Functions 没有」就是 `_headers` 生效的签名。由此推出 `5c5b60a`
（引入 `_headers`/`_routes.json` 的提交）**部署成功过**，第一次失败是 `180c73b`。

**2. 不要用 `Cache-Control` 判断 `_headers`**
Cloudflare 的 Browser Cache TTL（默认 4h = `max-age=14400`）会**覆盖** `_headers`
里的 Cache-Control。设了 `max-age=31536000, immutable`，线上仍是 14400 → 误判。

**3. 不要用 U+FFFD 找非法 UTF-8**
压缩后的 JS 里本来就有字面 U+FFFD（`t.REPLACEMENT_CHARACTER="\uFFFD"`），
那是合法码点。必须用 `new TextDecoder('utf-8',{fatal:true}).decode(buf)` 才算数。

**4. 308 不是「页面不存在」**
Pages 对目录页的 308 是补尾斜杠重定向，`/faq` → `/faq/`。要用 `-L` 跟随后再判断，
否则会把一堆正常页面误判成「未上线」。

### 真正的结论：Cloudflare 平台侧故障
决定性证据：**`3ed8bc6` 是纯文档提交**（只改 memory 文件），产出的 `dist` 与上一个提交
逐字节相同 —— 它也失败。内容导致的失败无法解释这一点。**失败与时间相关、与内容无关。**

佐证：1.5 秒就失败；报错是笼统的 "internal error" 而非 Cloudflare 对校验失败
会给的明确信息（如 "File X is larger than 25 MB"）。
同类报告：cloudflare/workers-sdk#13259（2026-04，发布流水线故障，与用户代码无关）。
